# 讨论3：项目计划

**项目名称**：工业报警洪水治理系统
**开发周期**：3 个迭代，每个迭代 2 天，共 6 天

---

## 一、项目范围计划

### （一）迭代设置与产能估算

本项目按作业要求设置 3 个迭代，每个迭代持续 2 天，总工期 6 天。团队 6 人全部投入，单个迭代可用人力为 12 人日，三个迭代合计 36 人日。

用户故事的大小采用故事点估算，点数取斐波那契数列中的 1、2、3、5、8 五档。按团队实际投入测算，一个迭代约可完成 10 至 12 点，三个迭代合计约 36 点。本次计划纳入的开发总量为 31 点，其余 5 点留作缓冲，用于吸收估算偏差。

### （二）纳入范围的用户故事

讨论 2 共形成 16 条用户故事。经团队共同评审，本次纳入 10 条，按迭代分配如下。

| 迭代 | 用户故事 | 故事点 |
|---|---|---|
| 第一个迭代（第 1–2 天） | US-01 报警记录生成 | 3 |
| | US-02 抖动报警 | 2 |
| | US-03 重复报警 | 2 |
| | US-04 源头标注 | 2 |
| | 小计 | 9 |
| 第二个迭代（第 3–4 天） | US-05 报警分组 | 5 |
| | US-06 关键报警保留 | 3 |
| | US-10 压缩效果对比 | 3 |
| | 小计 | 11 |
| 第三个迭代（第 5–6 天） | US-08 问题起点排序 | 5 |
| | US-12 问题起点展示 | 3 |
| | US-13 完整流程演示 | 3 |
| | 小计 | 11 |
| | **合计** | **31** |

### （三）不纳入范围的用户故事

其余 6 条本次不纳入，理由如下。

US-07 按工艺关联分组需要在压缩阶段引入测点之间的工艺拓扑关系，而 TEP 的工艺结构需要先行整理，工作量不易估计。本次压缩只采用时间维度聚类，变量维度暂以相关系数作近似处理。

US-09 排序依据可查看、US-11 报警组明细、US-14 首屏信息三条，属于结果的呈现方式与交互细节，不影响核心结论能否成立，本次暂不实现。

US-15 指标达标本身是项目的验收标准，不作为独立故事交付，相关内容并入各故事对应的验收测试用例。

US-16 效果对比面向管理层的效果评估，本次不纳入。

上述 6 条排除后，系统主链路仍然完整，即报警生成、报警压缩、源头定位、可视化演示四个环节均可交付。

## 二、用户故事优先级

按价值高低排列如下。

| 优先级 | 用户故事 | 点 | 排序理由 |
|---|---|---|---|
| 1 | US-01 报警记录生成 | 3 | 全部功能的数据前提，报警日志不能产出，其余功能均无法开展 |
| 2 | US-04 源头标注 | 2 | 缺少该标注列则无法计算源头定位的命中率，US-08 的验收将失去依据 |
| 3 | US-05 报警分组 | 5 | 系统的第一项核心价值，将上千条报警压缩至数十组 |
| 4 | US-08 问题起点排序 | 5 | 系统的第二项核心价值，也是与现有商用工具差别最大的部分 |
| 5 | US-13 完整流程演示 | 3 | 交付形态。缺少它，前四项成果无法展示 |
| 6 | US-10 压缩效果对比 | 3 | 使压缩结果可见，是验证 US-05 的手段 |
| 7 | US-12 问题起点展示 | 3 | 使定位结果可见，是验证 US-08 的手段 |
| 8 | US-06 关键报警保留 | 3 | 防止压缩误伤真实报警，属于质量约束 |
| 9 | US-02 抖动报警 | 2 | 提升数据真实性，取消后不影响主流程运行 |
| 10 | US-03 重复报警 | 2 | 同 US-02 |

需要说明的是，上表按价值排序，但迭代的实际分配与此并不完全一致。US-02 与 US-03 的价值排在末位，却被安排进第一个迭代。

原因在于这两条故事修改的是报警数据的生成规则，而数据集在本项目中只生成一次。若推迟到第三个迭代实施，前两个迭代已经完成的压缩率、保留率与命中率统计都需要重新计算。为避免返工，凡涉及数据生成逻辑的改动，均须在数据阶段一次完成。

因此本项目遵循的规则是：优先级依据价值确定，迭代分配在满足依赖关系与一致性的前提下，优先安排高价值故事。

## 三、迭代计划

每个迭代结束时须交付一个可运行的增量。

**第一个迭代（第 1 至 2 天）：报警数据基础**

本迭代完成 US-01、US-02、US-03、US-04，合计 9 点。迭代结束时可以演示：输入一段 TEP 过程数据，输出报警日志表，其中包含抖动报警、重复报警，以及标注每条报警与真实故障源头关联关系的标注列。

**第二个迭代（第 3 至 4 天）：报警压缩**

本迭代完成 US-05、US-06、US-10，合计 11 点。迭代结束时可以演示：页面并排显示压缩前后的报警，压缩率与关键报警保留率两个指标同时给出。

本迭代新增的报警组表与保留清单两张表，其字段命名与测点编号的编码方式须沿用第一个迭代确定的规范，以免后续环节无法对应。

**第三个迭代（第 5 至 6 天）：源头定位与全流程演示**

本迭代完成 US-08、US-12、US-13，合计 11 点。迭代结束时可以演示：执行一条命令，页面完整展示从原始数据到问题起点排序的结果。

源头定位需要回到原始时序数据中取数进行因果检验，取数所用的变量编码必须与第一个迭代统一格式后的编码一致，否则测点无法对应。

### （三）两项安排的说明

第一个迭代没有分配给 P6 的用户故事，因为看板功能需要等待第二个迭代产生数据后才能实施。为此安排 P6 在本迭代先行搭建看板界面骨架，以模拟数据完成三个视图的框架，待后续迭代数据就绪即可直接接入，避免在项目末期从零开始开发界面。

另外，团队规模相对于本期范围偏大，后半程出现人力闲置的可能性较高。人力闲置容易诱发自行扩充功能范围，这是项目失控的常见原因。将富余人力投入看板预研与测试用例执行，比事后禁止更为有效。

## 七、风险与应对

数据格式不一致。TEP 数据中 `d00.dat` 为转置存储，与其余文件的行列方向相反。该问题若不解决，后续所有实验的数据均无法对应。因此该项工作安排在第一个迭代的最前面。

报警生成延期。该环节是后续两个迭代全部工作的前提。若确实无法按期完成，则削减范围，取消抖动报警注入，优先保证基本的越限报警生成功能可用。

因果检验效果不佳。源头定位的命中率可能达不到目标值。退路是改用相关性分析与触发顺序相结合的方式进行排序，仍可完成交付。

估算偏乐观。6 天工期较为紧张。计划已预留 5 点缓冲，并在第三个迭代末尾保留半天用于端到端验证与演示准备，不另行安排开发任务。
